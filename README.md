# Tarolog: программные расклады карт

Небольшой автономный движок на TypeScript для шести раскладов. Он поддерживает две отдельные символические системы:

- `rider-waite-smith` — классическая 78-карточная колода Райдера—Уэйта—Смит;
- `full-moon-oracle` — 108-карточный «Оракул Полнолуния» Mystica & Agatta.

Движок:

- перемешивает полную колоду Райдера—Уэйта из 78 карт;
- поддерживает прямые и перевёрнутые положения;
- связывает карту со смыслом конкретной позиции;
- анализирует шесть смысловых пар, преобладающие масти, Старшие арканы, повторы рангов и придворные карты;
- возвращает JSON и готовую пару `system`/`user` сообщений для передачи любой LLM.

Доступные расклады:

| `spread` | Расклад | Карт | Статус |
|---|---|---:|---|
| `question-5` | Конкретный вопрос | 5 | стабильный |
| `yes-no-1` | Да или нет | 1 | стабильный |
| `yes-no-3` | Да или нет | 3 | стабильный |
| `timeline-7` | Прошлое — настоящее — будущее | 7 | рабочие позиции, ждут утверждения |
| `love-9` | Любовь и отношения | 9 | рабочие позиции, ждут утверждения |
| `celtic-cross` | Кельтский крест | 10 | стабильный |

## Запуск

Нужен Node.js 22.6 или новее. Установка зависимостей не требуется.

```powershell
npm.cmd start -- --question "Что мне важно понять о смене работы?"
```

Без `--spread` используется `celtic-cross`. Выбор другого расклада:

```powershell
npm.cmd start -- --spread question-5 --question "Что важно понять о новой работе?"
npm.cmd start -- --spread yes-no-3 --question "Стоит ли принимать это предложение?"
```

В PowerShell с запрещённым выполнением `npm.ps1` используйте `npm.cmd`, как в примерах выше, либо запускайте напрямую через `node src/cli.ts`.

По умолчанию используется Таро Райдера—Уэйта—Смит. Явный выбор колоды:

```powershell
node src/cli.ts --deck rider-waite-smith --question "Что мне важно понять о смене работы?"
node src/cli.ts --deck full-moon-oracle --question "Что скрыто в этой ситуации?"
```

Повторяемый результат для тестирования:

```powershell
npm.cmd start -- --question "Что мне важно понять?" --seed demo-1
```

Без перевёрнутых карт:

```powershell
npm.cmd start -- --question "Что мне важно понять?" --no-reversals
```

### Вероятность перевёрнутых карт

По умолчанию движок моделирует физическую колоду, в которой перед тасованием развёрнута примерно одна пятая карт (`reversalRate = 0.2`). Обычное тасование сохраняет ориентацию, поэтому перевёрнутые карты должны быть предварительно внесены в колоду намеренно. Значение 20% делает их заметным, но не доминирующим смысловым акцентом.

Вместо независимого броска вероятности для каждой вытянутой карты движок сначала фиксирует количество перевёрнутых карт во всей доступной колоде, перемешивает её и затем вытягивает карты без возвращения. В колоде Райдера—Уэйта—Смит это 16 из 78 карт, в «Оракуле Полнолуния» — 22 из 108.

Среднее число перевёрнутых карт в раскладах составляет примерно 0,2 из 1; 0,6 из 3; 1 из 5; 1,4 из 7; 1,8 из 9 и 2 из 10. Настройку можно изменить через `--reversal-rate`, а полностью отключить перевороты — через `--no-reversals`.

Выбор 20% является настройкой этого проекта, а не универсальным правилом Таро. Для сравнения, [Llewellyn приводит треть колоды как встречающуюся рекомендацию](https://www.llewellyn.com/blog/2013/12/what-are-tarot-reversals/), а [практическое руководство Angelorum предлагает 10–20% и разворот примерно одной пятой](https://angelorum.co/learn-tarot/7-ways-to-interpret-tarot-reversals/). Поскольку карты вытягиваются без возвращения, число перевёрнутых карт в раскладе следует [гипергеометрическому распределению](https://online.stat.psu.edu/stat414/Lesson07), а не серии независимых подбрасываний монеты.

Выход содержит исходные карты и трактовки в `cards`, найденные связи в `combinationSignals` и готовый ввод для языковой модели в `llmHandoff.messages`.

## Передача результата в LLM

`llmHandoff.messages` уже содержит всё необходимое:

- элемент с ролью `system` — подробную инструкцию, как читать позиции, перевёрнутые карты и комбинации;
- элемент с ролью `user` — конкретный вопрос и сырой результат текущего расклада.

Передайте эти два сообщения модели в том же порядке. Системная инструкция хранится в [`src/llm-instructions.ts`](./src/llm-instructions.ts) и автоматически включается в каждый результат. Она запрещает модели придумывать дополнительные карты, считать поворот второй карты перевёрнутым положением и выдавать вероятный итог за неизбежное событие.

### Программные действия LLM

В `llmHandoff.tools` возвращаются JSON Schema-описания четырёх функций:

- `tarot_read` — новый расклад; параметр `spread` выбирает одну из шести схем;
- `tarot_clarify` — от одной до трёх карт к одной неясной позиции;
- `tarot_followup` — отдельный трёхкарточный расклад на уточняющий вопрос;
- `tarot_expand` — однократный дочерний перерасклад вокруг выбранной позиции.

LLM получает правила вызова этих функций в системной инструкции. Она не должна сама дотягивать карты после каждого ответа, переделывать неприятный расклад или подменять исходную карту уточняющей.

Все шесть основных раскладов поддерживают три вида продолжения:

- `tarot_clarify` — 1–3 дополнительные карты к выбранной позиции;
- `tarot_followup` — короткий трёхкарточный расклад на новый связанный вопрос;
- `tarot_expand` — один полный дочерний перерасклад вокруг выбранной позиции. По умолчанию выбирается последняя позиция результата или направления; параметр `position` позволяет указать другую.

Дочерний расклад сохраняет колоду, режим перевёрнутых карт и исключает уже использованные карты. Для `yes-no-1` углубление использует `yes-no-3`; остальные расклады сохраняют исходную схему. Исходные карты не заменяются, а LLM обязана читать продолжение вместе с родительским раскладом.

| Исходный расклад | Позиция по умолчанию | Дочерний расклад |
|---|---:|---|
| `question-5` | 5 | `question-5` |
| `yes-no-1` | 1 | `yes-no-3` |
| `yes-no-3` | 3 | `yes-no-3` |
| `timeline-7` | 7 | `timeline-7` |
| `love-9` | 9 | `love-9` |
| `celtic-cross` | 10 | `celtic-cross` |

При создании расклада функция принимает короткие параметры `deck` и `spread`. Если `spread` не указан, используется `celtic-cross`; для обычного конкретного вопроса LLM проинструктирована выбирать `question-5`. Все последующие действия по его `readingId` автоматически используют ту же колоду. Для смены колоды создаётся новый независимый расклад: результаты разных систем могут сравниваться как разные символические перспективы, но не исправляют друг друга.

Ответы инструментов используют компактный формат. Каждая карта представлена массивом:

```text
[позиция, роль, название карты, "u" или "r", значение]
```

`u` означает прямое положение, `r` — перевёрнутое. Полные схемы функций, координаты расклада, английские названия, идентификаторы карт и повторная копия LLM-промпта в tool result не передаются. В контрольном раскладе размер результата сократился примерно с 19 500 до 3 600 символов — на 81%.

Для раскладов `yes-no-1` и `yes-no-3` дополнительно возвращается `verdict` в формате `[answer, confidence, score]`. Это программно рассчитанная символическая тенденция (`yes`, `no` или `unclear`), а не установленный факт. LLM получает отдельное правило сначала озвучить этот ответ, затем кратко объяснить условие по выпавшим картам.

Исполнитель функций хранит активные расклады в памяти:

```ts
import { TarotToolRuntime } from "./src/tool-runtime.ts";
import { tarotToolDefinitions } from "./src/tool-definitions.ts";

const runtime = new TarotToolRuntime();

// Передайте tarotToolDefinitions в параметр tools выбранного LLM API.
// Когда модель вернёт tool call, выполните его и отправьте результат обратно модели.
function executeToolCall(toolCall: {
  function: { name: string; arguments: string };
}) {
  return runtime.execute(
    toolCall.function.name,
    JSON.parse(toolCall.function.arguments),
  );
}
```

Один экземпляр `TarotToolRuntime` должен жить всё время диалога. Первый вызов возвращает `readingId`; последующие действия используют его, чтобы помнить исходный расклад и уже выпавшие карты.

Доступные трёхкарточные схемы:

- `clarity` — известное / скрытое / следующий шаг;
- `decision` — вариант A / вариант B / критерий решения;
- `relationship` — позиция вопрошающего / другой человек или среда / общая динамика;
- `progression` — источник / текущая фаза / ближайшее направление.

Для интеграции через отдельный долгоживущий процесс предусмотрен JSONL-сервер:

```powershell
node src/tool-server.ts --describe
node src/tool-server.ts
```

Вторая команда читает по одному JSON-объекту на строку:

```json
{"id":"call-1","name":"tarot_read","arguments":{"question":"Что мне важно понять о смене работы?","deck":"rider-waite-smith","spread":"question-5"}}
```

Ответ также занимает одну строку и содержит `result` либо `error`. Состояние и `readingId` сохраняются, пока процесс сервера работает.

Программное использование:

```ts
import { createSpreadReading } from "./src/spreads.ts";

const reading = createSpreadReading("Что мне важно понять?", "question-5", {
  deckId: "rider-waite-smith", // или "full-moon-oracle"
  seed: "optional-repeatable-seed",
});

console.log(reading.llmHandoff.messages);
```

## Метод

Позиции «Конкретного вопроса»: суть вопроса, скрытый фактор, препятствие, полезное действие, вероятный результат.

Однокарточное «Да или нет» даёт ответ и главное условие. Трёхкарточное использует основную тенденцию, изменяющий её фактор и итоговый вектор. Ответ вычисляется из смысловых маркеров карт и передаётся LLM вместе с исходными значениями, чтобы модель могла объяснить противоречия.

Рабочие позиции временной линии: корень прошлого, ключевое событие прошлого, наследие прошлого, настоящее, ближайшее развитие, дальнейшая тенденция, итоговое направление.

Рабочие позиции отношений: вопрошающий, другой человек, основание связи, потребности вопрошающего, наблюдаемая позиция другого, что объединяет, главное напряжение, полезный подход, вероятное направление. Формулировки намеренно не предлагают LLM выдавать скрытые мысли другого человека за факт.

Позиции основаны на разделе «An Ancient Celtic Method of Divination» из *The Pictorial Key to the Tarot* А. Э. Уэйта (1911): карта, которая покрывает вопрос; пересекающая сила; корона; основание; уходящее влияние; ближайшее влияние; сам вопрошающий; окружение; надежды и страхи; итог.

В оригинале отдельно выбирается сигнификатор. Здесь он намеренно опущен: для программного API вопрос выполняет роль контекста, а расклад остаётся стандартным десятикарточным. Поворот второй карты на 90° является частью схемы и не означает перевёрнутое положение; ориентация карты определяется отдельно.

Источник метода: [A. E. Waite, The Pictorial Key to the Tarot, Part III §7](https://original.sacred-texts.com/tarot/pkt/pkt0307.htm).

Состав «Оракула Полнолуния» соответствует 108-карточному изданию Mystica & Agatta: первые 36 образов основаны на Ленорман, остальные являются дополнительными символическими картами. Значения в коде сформулированы самостоятельно по символике и не воспроизводят текст авторского руководства. Список карт сверен по [галерее 108 карт](https://duhmaga.ru/taro/orakul-polnoj-luny.html) и [описанию русского издания](https://www.taroman.ru/product/orakul-polnoluniya/).
